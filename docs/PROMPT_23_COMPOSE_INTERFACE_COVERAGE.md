# ReiAnix — Prompt 23/29: matriz de cobertura da interface Compose

## Referência e escopo

Auditoria aplicada sobre a branch `main` em `f78c63b69e828fdb4690dfe72c26f716c5ec6427` (integração do Prompt 22/29). O ponto de entrada segue sendo `main.py` e a Activity Android continua baseada no template Flutter/Flet. Esta etapa migra os consumidores visuais restantes dentro do caminho Android/Compose; ela **não** remove globalmente Python, Flet, Flutter ou o fluxo de build híbrido, conforme a restrição do próprio Prompt 23.

O código real usa um host Compose persistente em `ReiAnixComposeLibraryHost`, um `NavHost` definido em `ReiAnixNavigation.kt`, um único `ReiAnixAppShell` e ViewModels que consomem os serviços/repositórios existentes. `main.py` mantém `NavigationController` e `page.views` como projeção compatível para o runtime legado. Essa projeção não deve fabricar uma segunda árvore Flet escondida para uma interface já controlada por Compose.

## Encontrado e corrigido nesta etapa

1. O `_build_screen("settings")` já usava um shell Flet vazio para a raiz de Configurações no Android, mas continuava construindo `SettingsView.build` para caminhos internos. O Compose já mantém a categoria selecionada em estado salvável, trata Back com `BackHandler` e contém implementações nativas para todas as categorias declaradas. O caminho Android foi corrigido para manter **todos** os níveis de Configurações como shell vazio de compatibilidade; a tela Flet fica disponível somente no fallback não-Compose.
2. `main.py` importava os seis módulos de telas Flet no nível do módulo, antes de saber se o host nativo estava disponível. Os imports de `HomeView`, `DetailView`, `OrganizeView`, `SettingsView`, `CollectorView` e `RecoveryView` foram movidos para dentro dos ramos de fallback que realmente constroem esses controles. No Android, os módulos visuais legados não precisam mais ser importados apenas para preparar a árvore Compose.
3. Os módulos Python de tela não foram excluídos. Permanecem como fallback não Android, e a lógica/serviços Python ainda necessários à inicialização híbrida, mailbox, compatibilidade e domínio não foram removidos prematuramente.
4. Foram adicionados contratos de regressão para importação condicional, ownership nativo dos níveis de Configurações, paridade entre categorias declaradas e gerenciadas por Compose, ligação das rotas ao host e existência desta matriz.
5. Foram conectados diálogos Compose de Linha do Tempo, Durações Incomuns e Maratona aos métodos `queryNativeTimelineGroups`, `queryNativeDurationAnomalies` e `queryNativeMarathonPlan` do ViewModel existente. Estados de carregamento, vazio, erro e repetição permanecem explícitos.
6. A tela Details passou a oferecer ações nativas para fixar/desafixar, editar/apagar a nota pessoal e corrigir identificação de episódio. As mutações usam as extensões SQLite já existentes ou a nova mutação transacional `setEpisodeManualIdentification`, atualizam as projeções nativas e preservam progresso, identidade de mídia e o schema v29.

## Limites e dependências explicitamente preservados

- `main.py`, Flet/Flutter e a infraestrutura híbrida permanecem necessários neste estágio; a remoção global do runtime foi explicitamente proibida pelo prompt e pertence a etapas finais.
- `views/home_view.py`, `views/details_view.py`, `views/organize_view.py`, `views/settings_view.py`, `views/collector_view.py` e `views/recovery_view.py` continuam válidos para o fallback não-Compose. Não foram apagados nem tiveram a lógica operacional interna removida.
- `core/ui.py`, `core/dialogs.py`, bridge, `LibraryStore`, serviços de negócio, scanner, SAF, MediaStore, SQLite canônico/schema v29, Artwork Engine, Media3/ExoPlayer, backups e progresso foram preservados.
- A matriz documenta integração por código e contratos. Ela não declara o projeto 100% Kotlin, nem substitui verificações de runtime que não foram realizadas. Ela **não** afirma testes em dispositivo/emulador, execução manual da suíte Kotlin/JVM, funcionamento em runtime não observado, nem que o projeto está 100% Kotlin. Esses pontos dependem dos workflows permitidos e das etapas finais da migração.
