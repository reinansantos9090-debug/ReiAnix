## B. Resumo executivo

**Conclusão:** o repositório ainda é híbrido, não é operacionalmente independente de Python/Flet/Flutter. Há uma base Kotlin significativa — Compose, Navigation, ViewModels, SQLite access, SAF/MediaStore scanners, AniList client, artwork rendering, operações SAF e Media3/ExoPlayer — mas os fluxos de inicialização, coordenação de varreduras, parte das projeções/mutações, settings/account, metadata localization, artwork producer, backup/recovery e CI continuam apoiados em Python ou na infraestrutura Flet/Flutter.

### Evidências mais fortes

1. android/app/src/main/kotlin/com/reiflix/reiflix_local/MainActivity.kt declara MainActivity : FlutterFragmentActivity. O arquivo explica que a Activity substitui a padrão do template Android gerado por Flet.
2. main.py importa e constrói AndroidBridge, ComposeLibraryBridge, ComposeSettingsBridge e ScanCoordinator. O arquivo tem 7.640 linhas no snapshot e segue como ponto de entrada do runtime Python.
3. pyproject.toml fixa Python >=3.12,<3.13, flet==0.86.5 e Pillow. O build APK configura Python 3.12, Flutter 3.44.8, instala Flet, prepara o template Flet, verifica serious_python e chama flet build apk.
4. core/library_store.py declara SCHEMA_VERSION=29 e o caminho data_dir/library.sqlite3. Kotlin usa filesDir/data/library.sqlite3, DATABASE_FILE_NAME library.sqlite3 e EXPECTED_SCHEMA_VERSION=29. O banco Kotlin abre arquivo existente e valida um contrato empacotado; o workflow gera esse contrato a partir de LibraryStore via script Python. A compatibilidade do caminho/schema está alinhada, mas bootstrap e migrações não são independentes.
5. MainActivity publica scan_request por NativeMailbox; o próprio comentário no código diz que o ScanCoordinator Python decide se/quando o scanner será executado. Portanto, classes scanner Kotlin não comprovam coordenação nativa completa.
6. core/artwork.py importa PIL.Image e PIL.ImageOps e mantém workers, cache, validação de imagem, registro de arte, miniaturas e publicação. Kotlin contém Coil e VideoThumbnailExtractor, mas o produtor do pipeline ainda é Python.
7. O motor Media3/ExoPlayer e a persistência de progresso têm operações nativas concretas. Isso não elimina a dependência Python da inicialização da aplicação, da coordenação de episódios e de várias projeções de histórico.

### Principais bloqueadores

- Activity/host inicial ainda depende de Flutter; não existe caminho de launcher nativo comprovado sem runtime híbrido.
- LibraryStore ainda é o proprietário da inicialização e migração do banco v29; Kotlin abre/valida um arquivo existente.
- ScanCoordinator e reconciliação continuam no core Python.
- Dois conjuntos de implementações podem escrever no mesmo arquivo SQLite: LibraryStore em Python e vários serviços Kotlin. O arquivo é uma única fonte física, mas os owners operacionais e regras de concorrência ainda precisam ser unificados.
- ComposeLibraryBridge e ComposeSettingsBridge produzem snapshots/command results que a interface Kotlin ainda consome.
- AniList, localização pt-BR, ArtworkEngine, backup, recuperação e módulos de organização continuam no caminho Python.
- O build obrigatório não é nativo standalone: empacota o host Flet/Flutter/serious_python.

## E. Grafo textual dos fluxos reais

### Inicialização e UI

1. Android Launcher → AndroidManifest.xml → MainActivity : FlutterFragmentActivity → Flutter host preparado pelo template Flet → runtime Python/Flet → main.py.
2. main.py → settings/configuração e LibraryStore → LibraryService/ScanCoordinator e serviços de domínio → ComposeLibraryBridge/ComposeSettingsBridge → arquivos JSON de snapshot e resultados no diretório reianix-compose → ViewModels/Compose host → Compose Navigation/screens.
3. MainActivity cria/gerencia ReiAnixComposeLibraryHost e ViewModels Kotlin; isso entrega um shell Compose real, mas o host Flutter segue sendo a base da Activity/processo.
4. Ação de tela → ViewModel/Repository nativo quando implementado; para comandos legados, a ação é serializada em JSON e publicada por NativeMailbox; AndroidCommandDispatcher/FileObserver processa comandos e publica eventos, que são observados pelo AndroidBridge Python. O evento de retorno pode mudar um snapshot projetado no Compose.

### SQLite e biblioteca

1. main.py → LibraryStore(data_dir) → SQLite connection, schema inicialização/migrações v29 → data_dir/library.sqlite3.
2. Gradle workflow → generate_native_sqlite_test_fixture.py → contrato nativo em android/app/src/main/assets/native-sqlite-contract-v29.json.
3. Kotlin ReiAnixSqliteDatabase → filesDir/data/library.sqlite3 existente → valida tabelas/colunas/índices/constraints/FKs; não cria ou migra o banco.
4. Kotlin ReiAnixSqliteLibraryRepository e serviços LibraryQuery/PersonalList/Consumption/Settings executam queries ou mutações nativas específicas no mesmo arquivo.
5. Python LibraryStore/LibraryService continuam responsáveis por partes do catálogo, matching, metadados, reconciliação, settings e backup. A única fonte física não significa owner lógico único: atualmente existem conexões e implementações em duas linguagens; a sequência de migração deve fechar semânticas e coordenação antes de retirar Python.

### Scanner e armazenamento

1. Activity/receivers/ContentObserver → StorageAuthorization/SAF/MediaStore/BroadStorageScanner → NativeScanController/NativeScanRunner → batches/progress/terminal result.
2. MainActivity também publica scan_request via NativeMailbox → core/android_bridge.py → Python ScanCoordinator → LibraryService/LibraryStore.
3. O fluxo SAF pode executar indexação no repositório SQLite Kotlin e marca ownership nativo. Se a transação nativa falha, NativeScanRunner preserva o snapshot de descoberta e publica fallback por mailbox ao pipeline Python; status parcial deve impedir reconciliação destrutiva. PR #160 é a mudança integrada relevante para esse comportamento.
4. SAF file operations (list/create/rename/move/delete) usam ContentResolver em Kotlin, mas reconciliação da identidade dos arquivos ainda publica eventos para o runtime Python.
5. Migração completa precisa tornar a coordenação, ingestão, cancelamento, reconciliação e publicação de estados Kotlin, não duplicar scanners nem simplesmente descartar o fallback.

### AniList, artwork e imagens

**Atualização do Prompt 06/29:** os fluxos nativos passam pelo cliente GraphQL e serviço Kotlin; a sinopse original/localizada é persistida no repositório canônico e um evento mínimo pós-commit solicita ao ArtworkEngine existente materializar as URLs. Este evento não delega consulta ou matching AniList ao Python. O cliente/LibraryService Python ainda permanece no caminho Flet/legado, e o produtor de artwork ainda é Python; portanto a classificação global permanece PARCIAL, não NATIVO COMPLETO.

1. Em caminhos atuais, LibraryService Python → AniListClient Python/GraphQL → cache e normalização/localização de descrição → refresh metadata → ArtworkEngine Python → download/cache/validação via Pillow → persistência e eventos → snapshot Compose.
2. Há também ReiAnixAniListClient.kt e ReiAnixAniListIntegrationService.kt, que implementam busca, atualização, associação manual e auto-match via serviços nativos. A coexistência não prova que o fluxo de produção migrou todo para Kotlin.
3. Kotlin Coil/ReiAnixLocalArtwork e VideoThumbnailExtractor cuidam da apresentação e de parte da extração local; core/artwork.py continua responsável por partes centrais do pipeline produtor.

### Player e consumo

1. UI ou AndroidBridge solicita player → NativeCommandDispatcher/MainActivity validam a solicitação e a URI → NativePlayerActivity/Media3 ExoPlayer → NativeSubtitleResolver/PlayerMediaPolicy/metadata store.
2. NativePlayerActivity correlaciona requestId, playerSessionId, playerGeneration e transitionGeneration e grava progresso por ReiAnixConsumptionService no SQLite canônico.
3. Eventos de transição/resultado/diagnóstico podem ir ao NativeMailbox e ao consumidor Python. A reprodução da URI é nativa, mas a jornada completa de lançamento, episódio seguinte/anterior, estado da Home e histórico precisa ser eliminada da ponte antes do cutover.

### Backup, recuperação e build

1. Backup atual: Flet/settings/recovery views → core/backup.py e core/recovery.py → snapshot/manifest/checksums/SQLite canônico. Kotlin quickCheck/schema inspection não substituem exportação/restauração.
2. Build atual: workflow → Python 3.12 + requirements/Flet CLI 0.86.5 + Flutter 3.44.8 + Android SDK/JDK17 → gerar identidade e contrato SQLite via scripts Python → baixar/descompactar template Flet → aplicar overlay android/ → verificar serious_python → flet build apk → APK e ZIP de distribuição.
3. Caminho desejado: Gradle nativo → Kotlin/Compose/services → SQLite existente e APIs/Android SDK; sem Flet, Flutter, serious_python, main.py ou scripts Python no build/distribuição.

## H. Critérios verificáveis para declarar independência 100% Kotlin

Nenhum critério abaixo é satisfeito pelo simples fato de uma tela já usar Compose. A migração final deve reunir evidência para cada requisito:

1. Manifest/launcher: MainActivity não herda de FlutterFragmentActivity; cold start, rotação, retorno ao foreground e deep links funcionam sem Flutter.
2. Runtime: APK instalado executa todas as funções sem Python, Flet, Flutter, serious_python, main.py, plugins Flet ou arquivos intermediários gerados por scripts Python.
3. Build: workflow constrói APK via Gradle/Android SDK/JDK, sem instalar Python/Flet/Flutter; APK e ZIP (se ainda forem distribuição prevista) associados ao SHA exato e baixáveis.
4. Dados: Kotlin cria/valida/atualiza o mesmo data/library.sqlite3; schema v29 preservado inicialmente; migrações futuras têm caminhos de upgrade reversíveis/testados e não exigem limpar dados.
5. Ownership: cada tabela/campo e operação tem uma autoridade lógica clara; não existem dois escritores de domínio concorrentes sem protocolo explícito.
6. Storage: permissão URI SAF persiste/restaura; MediaStore e pastas continuam encontráveis; scans incrementais/cancelados/parciais não causam remoção indevida.
7. UI: Home, Library, Details, Search, My List, Organize, Settings, Storage, Account e Recovery carregam estados reais Kotlin, com erro/empty/loading, e suas ações persistem sem snapshots Python.
8. Metadata/arte: busca, associação e atualização AniList; sinopses pt-BR/cache; download/cache/capas/miniaturas e publicação funcionam offline/online sem Pillow.
9. Player: início/URI/legendas/next-previous/progresso/histórico e session transitions seguem Kotlin; request/session/generation impedem eventos antigos e progresso incorreto.
10. Organização: regras de parsing, gênero, coleções, renomear/mover e matching têm paridade verificada, sem executar regras Python.
11. Conta/settings/backup: ações e preferências não usam NativeMailbox/ComposeSettingsBridge; backup e recovery mantêm compatibilidade e têm fluxo explícito de segurança.
12. Pontes: NativeMailbox, NativeCommandDispatcher, ComposeLibraryBridge e ComposeSettingsBridge removidos somente depois que todas as referências e consumidores desaparecerem e os contratos forem cobertos por serviços nativos.
13. Testes: testes de regressão mantidos; testes Kotlin/JVM seguem manualmente acionáveis via workflow_dispatch, sem serem executados nesta fase; nenhuma suíte instrumentada/emulador nova; CI requerido verde para SHA final.
14. Higiene: busca estática por Flet, Flutter, serious_python, main.py, Pillow, imports core/views e diretórios gerados não encontra dependência funcional no runtime/build (referências apenas em docs/fixtures arquivados devem ser justificadas).
15. Distribuição: artefato APK é o resultado do build native-only, instalação/upgrade sobre dados reais preserva biblioteca, permissões, progresso, conta/configurações e backups.

Migrações de upgrade e outros contratos continuam dependendo de Python: comandos/projeções de biblioteca/configurações, eventos de mailbox, partes do produtor de metadados/artwork e backup/recuperação. Portanto, o runtime integral e o build oficial ainda não são certificados sem Python/Flet/Flutter; não se removeram `main.py`, `core/`, `views/`, as dependências oficiais ou os testes Python nesta etapa.

As reduções funcionais desta etapa são delimitadas: os lotes de mídia preparados em `NativeIndex` deixam de transportar seus arrays de documentos pelo `NativeMailbox` em mensagens de sucesso (o consumidor Python já os ignorava quando `nativeLibraryIndexOwner=true`) e a projeção Compose passa a derivar o estado de scan de todos os snapshots nativos SAF/MediaStore/Broad Storage. A notificação compacta de erro e os eventos terminais/de progresso permanecem para compatibilidade, logo a mailbox ainda participa do runtime híbrido.

A matriz de dependências, os critérios de saída e os bloqueios de cutover deste snapshot estão em `docs/PROMPT_28_RUNTIME_CUTOVER_STATUS.md`. Até os consumidores obrigatórios restantes serem migrados e os workflows oficiais comprovarem o build do aplicativo completo sem Python/Flet/Flutter, o Prompt 28 não pode ser certificado como runtime nativo integral.

## Follow-up Prompt 28.2/29 — escopo de indexação MediaStore (17/10/2026)

A verificação anterior do Prompt 28 classificava MediaStore como diagnóstico-only, mas o código tinha um defeito adicional: o runner não enviava os escopos SAF exigidos pelo scanner, e o nome de origem usado pelo staging MediaStore divergia do nome usado para publicar/ler as gerações. O follow-up liga as árvores `folders` persistidas e validadas à varredura, alinha a origem ao `NativeIndex.SOURCE_MEDIASTORE` e encaminha snapshots por volume ao mesmo `ReiAnixLibraryService`/SQLite canônico com resultado transacional registrado.

A indexação MediaStore só opera quando os caminhos podem ser comprovados dentro de árvores SAF persistidas e legíveis de `ExternalStorageProvider`; caminhos e volumes fora dessas raízes são ignorados. A autorização é consultada antes e depois da descoberta e novamente antes de reconciliar cada volume. Se uma raiz externa configurada estiver inacessível ou tiver sido revogada, registros positivos de escopos legíveis podem ser atualizados, mas a reconciliação de ausências fica desativada com aviso terminal. A identidade física volume+caminho permite reconhecer observações SAF/MediaStore da mesma mídia. Quando um registro existente pertence à árvore SAF, a atualização não substitui seu URI de reprodução nem seu caminho relativo à árvore. A reutilização de snapshots também exige a assinatura atual das raízes autorizadas e um recibo de commit canônico. Scans parciais não reconciliam ausências; uma árvore `primary:` só representa o volume inteiro quando foi selecionada e validada explicitamente. Antes da API 29 o caminho delimitado por MediaStore informa bloqueio explícito por não conseguir provar escopo com as colunas disponíveis.

Broad Storage permanece diagnóstico-only: a permissão global de armazenamento não identifica a biblioteca selecionada e não pode autorizar reconciliação global do catálogo. O runtime e o workflow oficial ainda são híbridos; esses changes de indexação não certificam independência de Python/Flet/Flutter nem substituem as migrações de upgrade da base, os contratos de mailbox, AniList/artwork e backup/recovery. O SHA e os resultados finais de CI desta etapa devem ser registrados somente depois de os workflows do SHA final terminarem.
